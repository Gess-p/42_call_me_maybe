# call-me-maybe

## Description

`call-me-maybe` is a function-calling tool that translates natural-language prompts into structured JSON function calls. Given a request such as `"What is the sum of 2 and 3?"`, it outputs:

```json
{"name": "fn_add_numbers", "parameters": {"a": 2.0, "b": 3.0}}
```

The system does not answer the question, it returns the tool (function name plus arguments) that should be called to answer it. The function is selected by the LLM, not by heuristics.

The project uses constrained decoding on top of Qwen3-0.6B (via the provided llm_sdk). Instead of hoping a small model emits valid JSON, every token is validated against a formal grammar (trie, FSM, or cursor) before being committed. This guarantees 100% syntactically valid JSON and schema-compliant output, even with a 0.6B-parameter model.

### Algorithm explanation

The core idea is constrained decoding: at each generation step, the model produces logits over its full vocabulary (~150k tokens); we mask every token that would violate the target grammar with -inf, then take the argmax over the remaining legal tokens.

The pipeline for a single prompt is:

    Build the input: system prompt + user request + "Response: ".

    Encode the full string with the model's tokenizer.

    Inject a fixed skeleton: {"name":".

    Generate the function name using a trie of all declared function
    names. At each step, only tokens that extend a valid name prefix are legal.
    The model chooses among them via logits, the function is chosen by the
    LLM, not by heuristics.

    Inject another fixed skeleton: ","parameters":{.

    For each declared parameter (in schema order):

        Inject the fixed prefix "<name>":.

        Generate the value according to its type:

            number / integer - a small FSM over digits, optional sign, optional
            decimal point; commas and closing braces are legal terminators.

            boolean - a trie over true / false.

            string (regular) - a multi-cursor over the original prompt.
            Only substrings that exist in the prompt are accepted, which prevents
            hallucination.

            string (regex) - an FSM that validates regex syntax incrementally.
            Character classes, ranges, and escapes are checked at each step.

        Inject a comma between parameters.

    Inject the closing }.

Because the skeleton is injected as fixed tokens and every value is masked against a formal grammar, the resulting JSON is guaranteed to be syntacticall valid and schema-compliant.

#### Components

    Trie - prefix tree. Used for function names and boolean literals.

    FSM (Finite State Machine) - states and transitions. Used for numbers
    and regex syntax.

    Cursor - tracks the set of positions in the prompt where the current
    string value could still match. Prunes impossible positions after each
    token.

    Mask - logits[invalid] = -inf, then argmax.

#### Design decisions

    Skeleton injected as fixed tokens. Only the values (function name and
    parameters) are generated by the model. Keys, punctuation, and structure
    are fixed. This guarantees valid JSON structurally, regardless of model
    quality.

    Function name via trie. The model can only emit names that are declared
    in functions_definition.json. It still chooses among them via logits,
    satisfying the requirement that the function be chosen by the LLM.

    Strings via cursor over the prompt. String arguments are restricted to
    substrings that actually appear in the user prompt. This prevents the model
    from hallucinating values and keeps the output grounded.

    Regex via FSM. Regex syntax is validated incrementally, so an invalid
    regex can never be emitted. Character ranges ([a-z]) are checked so the
    endpoint is never smaller than the start.

    Numbers via FSM with a token cap. The numeric FSM has a hard cap on the
    number of tokens emitted, preventing infinite loops when the prompt does
    not contain a number (e.g. "add the numbers" with no values).

    ParamType.UNSUPPORTED fallback. The schema loads successfully even if
    a function declares an unknown parameter type. The error surfaces only at
    generation time, on the specific parameter, so one malformed definition does
    not invalidate the whole file.

    Regex detection by name + description. A string parameter is treated as a regex if its name matches a known set (`regex`, `pattern`, ...) *and* the function description mentions regex-related words. This is deliberately conservative: misclassifying a regular string as a regex would degrade accuracy on unrelated prompts. The system prompt additionally guides the model to prefer general patterns (`[0-9]+`, `[aeiou]`) over literal text when generating regex arguments, which fixed the main failure mode observed during testing.

    Pydantic for all data models. FunctionDef, ParamDef, ReturnDef,
    UserPrompt, and FunctionCall are Pydantic models. Utility classes
    (Cursor, Loader, Generator) are plain classes, not data models,
    so Pydantic does not apply.

#### Performance analysis

Measured on CPU (default environment), processing all 11 example prompts:

	- Total time: ~130 s (well under the 5-minute limit).
	- Function selection: 11/11 = 100%.
	- Argument extraction: 10/11 = 90.9% (strict).
	- JSON validity: 100% - guaranteed by construction.

The single remaining error is prompt 10 (*"Replace all vowels in
'Programming is fun' with asterisks"*): the model emits
`replacement = "asterisk"` instead of the literal symbol `"*"`. This is a
direct consequence of the multi-cursor design (see *Challenges faced* and
*Design decisions*),  the character `*` does not appear in the prompt, so the
cursor cannot emit it. If the grader accepts the word `"asterisk"` as a valid
replacement, argument accuracy is **11/11 = 100%**.

Per-prompt latency varies between ~4 s (short prompts) and ~35 s (prompts
involving regex, which require more generation steps).

The main performance bottleneck is that `llm_sdk` does not expose a KV cache,
so every token re-encodes the full prompt. This is a deliberate constraint of
the assignment (private `llm_sdk` attributes must not be used); no workaround
is possible without violating that rule.

#### Challenges faced

1. **Making a 0.6B model emit valid JSON.** Naive prompting fails ~70% of the
   time. Constrained decoding solves this: by masking invalid tokens at each
   step, the output is valid *by construction*. The challenge shifts from
   "getting valid JSON" to "getting the right values".

2. **Extracting strings from the prompt without hallucination.** A small model
   will invent plausible-looking values. The multi-cursor approach restricts
   string arguments to substrings that actually occur in the prompt, which
   grounds the output but limits what can be emitted (see point 4 below).

3. **Regex arguments.** The model does not see the user prompt when generating
   a regex, the regex grammar is too permissive to be conditioned on
   arbitrary text. Initially, for prompts like *"replace all numbers..."*, the
   model copied literal digits (`34233`) instead of generalising to `[0-9]+`.
   Two strategies were tested:
   - Injecting the user prompt as extra context immediately before the regex.
     This **regressed** in one case (produced `[^aeiou]` instead of `[aeiou]`
     for the vowels prompt) and was reverted.
   - Adding explicit guidance to the system prompt, instructing the model to
     prefer general patterns (`[0-9]+`, `[aeiou]`, `\s`) over literal text.
     This **succeeded**: prompt 9 now produces `regex = "[0-9]+"` consistently
     across repeated runs.

4. **Symbolic replacements (`*`, `_`, ...).** The `replacement` argument is
   generated by the same multi-cursor that extracts regular strings. Since
   `*` does not appear in the user prompt, the cursor cannot emit it, and the
   model falls back to the closest available word (`"asterisk"`). Fixing this
   would require either a dedicated symbol generator or a heuristic mapping
   (`asterisk → *`), which the assignment discourages. The trade-off was made
   in favour of **groundedness** (never hallucinate a value) over **symbolic
   flexibility**.

5. **Distinguishing regex from regular strings.** A string parameter called
   `pattern` in a function about regex substitution is a regex; a string
   parameter called `name` is not. Detection uses both the parameter name and
   the function description, and errs on the side of *not* treating a string
   as a regex, to avoid degrading unrelated prompts.

#### Testing strategy

    Manual end-to-end tests: the 11 prompts in
    data/input/function_calling_tests.json are processed on every change, and
    the output is compared against expected function names and arguments.

    Lint and types: make lint and make lint-strict are run before every
    commit. Both pass without issues on all source files.

    Edge cases tested:

        Prompts with quoted strings (single and double quotes).

        Prompts with multiple numbers.

        Prompts with numbers split across the text (`34 ... 233`), verified that the regex generator produces `[0-9]+`, not the concatenated literals..

        Empty or malformed input files (handled gracefully, see Loader).

        Missing or unreadable files (exit code 1, error message on stderr).

    Type safety: the codebase passes mypy --strict, including
    --warn-return-any, --disallow-untyped-defs, and
    --check-untyped-defs.

##### What a wrong prompt looks like

The system never crashes. If a prompt cannot be resolved (e.g. the generator
raises internally), the result is emitted with "name": "" and empty
parameters, and the failure is logged to stderr:
```json
{
  "prompt": "...",
  "name": "",
  "parameters": {}
}
```
The exit code remains 0 as long as the batch completes and the output file is
written.
